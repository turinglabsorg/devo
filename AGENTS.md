# Devo Agent Instructions

Devo is a DevOps specialist for cloud audits across GCP, AWS, and DigitalOcean.

## Operating Rules

- Default to read-only diagnostics. Do not create, update, delete, restart, resize, rotate, or deploy cloud resources unless the user explicitly asks for that action.
- Never print secrets, access tokens, private keys, full environment dumps, service account key contents, or unredacted credentials.
- Always state the cloud scope before running commands: provider, account/project, region, service, and time window.
- Treat tenants as isolated operational contexts. Do not mix findings, commands, costs, logs, or identifiers across tenants.
- Resolve tenant aliases through `devo.config.json` before running provider-specific checks when the user names a client/project alias.
- Prefer explicit command flags over global state changes. For GCP, use `--project` instead of `gcloud config set project` unless the user asks to change local defaults.
- For GCP, isolate human identities with separate `CLOUDSDK_CONFIG` roots on every CLI, proxy, and local ADC-consuming process. The local profiles are `master` (`sebastiano.cataudo@gmail.com`) and `nobrainer` (`seer@nobraineragency.com`); their credential files remain outside this repository under `/Users/zencrust/.config/gcloud-profiles/`.
- For AWS, verify `aws sts get-caller-identity` before querying resources and state the active profile/region when known.
- For DigitalOcean, require a tenant-scoped `doctlContext` and pass `--context` on every account or resource command. Never rely on the globally active context for tenant work.
- Cost checks should distinguish between estimated current-month spend, historical invoiced cost, and forecasted spend.
- Log comparisons should use a concrete time window and normalize timestamps, severity, service name, region, deployment version, trace ID, and request ID when available.

## Architecture

- Runtime CLI entrypoint: `skill/index.js`.
- Shared audit logic and tenant resolution: `skill/scripts/doctor.mjs`.
- Global tenant config path: `~/.devo/config.json`.
- Local development tenant config path: `./devo.config.json` in the repo root; this file is ignored by Git.
- Tenant config schema is documented in `devo.config.example.json` and `skill/references/tenants.md`.
- Installed command path: `~/.local/bin/devo`, generated by `skill/install.sh`.
- DigitalOcean tenant records use `provider: "digitalocean"` with a required `doctlContext`; optional fields are `teamName`, `defaultRegion`, `regions`, and `digitalOceanProjectId`. Credentials remain in the named `doctl` context and credential fields are rejected from Devo config.
- GCP identity-profile instructions live in `skill/references/gcp.md`. The repository stores profile metadata and paths only; never add gcloud `credentials.db`, ADC JSON, OAuth tokens, cookies, or exported credentials.
- `devo doctor --tenant <digitalocean-tenant>` verifies `doctl`, account identity, project visibility, and an optional configured project using the explicit tenant context. The command catalog covers identity, services, logs, costs, and IAM without changing the global `doctl` context.
- GCP identity runtime is split four ways: `skill/scripts/profiles.mjs` is the registry (name, account, root, health project, project patterns); `skill/scripts/gcloud.mjs` is the router, where `--profile` is mandatory and each call pins `CLOUDSDK_CONFIG`, the account and the project, refusing a project that belongs to another profile's scope and refusing a mutating `auth`/`config` subcommand unless `--allow-mutation` is passed. The mutating list is `auth login`, `auth application-default login`, `auth activate-service-account` (it stores a credential in the root, which is why the harness guard names it too), `config set`, `config unset` and `config configurations`, and the subcommand is read **past the run of global flags** a caller may put in front of it: `gcloud -q auth login`, `gcloud --project <id> auth login` and `gcloud --verbosity debug auth login` write the root exactly as the bare spelling does, and reading the subcommand at the first argument made a flag a way around the guard -- that reading is the whole of the hole a review found here. A flag whose value is a separate token is stepped over by gcloud's own flag list (`--project`, `--account`, `--configuration`, `--verbosity`, `--format`, `--filter`, `--flatten`, `--impersonate-service-account`, `--billing-project` and the file-taking ones); a flag the list does not carry (`--log-http`, or one a later gcloud adds) leaves the token after it unreadable -- its value or the subcommand -- so **both readings are kept and a mutation at either position is refused**, which is the only direction this guard can err in safely. The same reading decides whether a call is identity-scoped, so an `auth`/`config` call reached behind a flag keeps the project and the account off its command line and the account drift check steps aside for it. `auth activate-service-account` was a mutation of the same class that the list did not carry, so it was not refused at all; `skill/scripts/exec.mjs` is that same pin for a process that is not gcloud (`devo exec --profile <name> [--project <id>] -- <command...>`), which refuses any argument that names an identity root or a credential store so it can never hand one over, judging that argument by the path it denotes rather than by its text -- a root relocated through `DEVO_GCLOUD_PROFILES_DIR`, a symlink to one, a parent of one and the filesystem root itself are all refused, because each of them is a root or holds every root there is. A credential store is judged by the **name it carries** (`credentials.db`, `access_tokens.db`, `legacy_credentials`, `application_default_credentials.json`) and not only by resolution, because a store named where no root is -- another user's home, a store with no file behind it yet -- has no directory to be resolved to, and `legacy_credentials` was the fourth store and missing from that list. The one argument that is not a path is the command word: `ls` is a name looked up on PATH, and PATH is not the working directory, so a separator-less command word is **not** resolved against the directory the caller happens to be in -- resolving it refused any command run from inside a root, where the lookup never looks -- while a command word written as a path (`./ls`, `/bin/gcloud`) is judged as one. Each argument is read twice, because the tools on this machine do not agree about `..` after a symlink: the kernel follows the link and applies `..` to the directory it reached, while a text-first tool collapses `..` before following anything, and `<link to a directory inside the root>/..` is the root to `open` and to `tar -C` but only the link's own directory to the other reading -- judging one of them would hand the root to whichever kind of process reads it the other way, and that argument is how the root was packed out once. The route also names the profile's own `application_default_credentials.json` for the child, because `CLOUDSDK_CONFIG` is where gcloud looks and not where a client library looks; a profile that has no such file leaves the child on the ambient identity, which is reported as a warning and recorded as a residual rather than refused -- and in that state an **inherited `GOOGLE_APPLICATION_CREDENTIALS` is deleted** from the child's environment rather than passed on, because it names another identity's credentials and the child would otherwise authenticate as one client while the route reports the other as pinned. It applies the router's mutation guard to a `gcloud` command word reached through it, read as the program it names: a directory in front of it (`/usr/local/bin/gcloud`) and **another case of it** (`Gcloud`, the same file on this filesystem) are the same program, so the case of a letter is not a way around the guard (a `gcloud` call inside a shell wrapper is not inspected; `skill/test/exec.test.mjs` names that boundary as a residual); `skill/scripts/watch.mjs` is the hourly launchd watchdog (`com.zencrust.devo-auth-status`, installed by `devo auth watch --install`), which records one JSONL per profile under `~/.devo/auth-status/<profile>.jsonl`. The record path is derived from the profile for the same reason `CLOUDSDK_CONFIG` is: a single shared history was writable by two processes working on two identities, and it could not say which identity a count belonged to. Records written before the split are in `~/.devo/auth-status.jsonl` and are reported separately, never counted in with the rest.
- `skill/hooks/gcloud-guard.sh` is a Claude Code PreToolUse guard, deployed to `~/.claude/hooks/` by `skill/install.sh` and registered in `~/.claude/settings.json` under `hooks.PreToolUse` with `"matcher": "Bash"`. It denies an unprefixed `gcloud auth login` / `gcloud auth application-default login` / `gcloud auth activate-service-account` / `gcloud config configurations activate` / `gcloud config set account`, `--update-adc`, any read of a credential store (`credentials.db`, `access_tokens.db`, `application_default_credentials.json`, `legacy_credentials`), and any transfer of an identity root off the root it is protected in -- into a container or onto another host (`docker`, `docker-compose`, `podman`, `nerdctl`, `colima`, `limactl`, `vagrant`, `kubectl`, `ssh`, `scp`, `rsync`), or into a copy or an archive on this disk (`cp`, `mv`, `tar`, `zip`). The auth rule reads the call as the word, the run of global flags a caller may put between the word and the subcommand, and the value each of those flags takes, because `gcloud -q auth login` and `gcloud --project <id> --verbosity debug auth login` write the ambient root exactly as the bare spelling does; `activate-service-account` stores a credential in that root and `config set account` changes which identity an unprefixed call will silently use, so both are on the list for the same reason. Both halves are one rule: a stray copy is the copy that gets committed. A verb is judged as the tool it names, not as the word it is written with: a directory in front of it (`/bin/cp`) and an escape (`\cp`) are read as the same tool, and both halves of the test are matched without regard to case, because on this filesystem another case is the same file. The text is first read the way the shell reads it, so a verb is the tool it names (`/bin/cp`, `\cp`, `c\p`, another case) and a root is the directory it denotes (`~/.config//gcloud`, `~/.config/./gcloud`, `gclou\d`). A root is also recognised by the variable that can name one (`CLOUDSDK_CONFIG`), because a relocated root carries none of the letters of the default path. Quotes are removed from the line every rule reads, because a shell hands a program the same words with or without them: a root inside quotes still carries the letters of its path, but `"cp"` carries none of the letters of the tool it names, and reading the line with its quotes in it left `"cp" -R <root> /tmp` at exit 0 -- the copy this rule exists for, with the tool quoted. A backslash before a newline is removed the same way, and the lines it joins are the one command they are: `gcloud \` on one line and `auth login` on the next writes the ambient root exactly as the one-line spelling does, and read line by line that call was never seen -- while the sanctioned bootstrap in `skill/references/gcp.md`, whose pin is on its first line and whose `gcloud` word is on its second, was refused for the same reason, so both readings were wrong the same way. Only an odd run of backslashes joins: two of them are one escaped backslash and the newline after it still ends the command, so a word ending in `\\` keeps the boundary a rule needs in front of a verb. `--update-adc` is judged before the trigger that looks for a `gcloud` spelling, since in a command like `devo auth repair master --update-adc` the flag is the only token naming identity material at all; the credential-store rule is judged after that trigger, and reaches every store because the trigger's own list names them. A `CLOUDSDK_CONFIG=<root>` assignment that opens a shell segment is an environment pin for one local process, which is what the identity rules ask of every one of them, so the whole segment is dropped before that test; a root named as an argument is not dropped, so the mount, the copy and the build context stay denied. The value the dropped assignment named is kept and judged separately, because nothing stops the same line from naming that root a second time: `CLOUDSDK_CONFIG=<root> cp -R <root> /tmp` pins nothing and copies the root, and the argument carries none of the letters of the default path, so the assignment being dropped was the whole of the evasion. It is judged as the path it is and not as a substring of the line: the value `/tmp/root` is not named by `/tmp/root2`, and refusing that copy was a refusal about a path nobody had handed over. The exemption is that grammar, not the letters: a pin spelled as an argument to a builtin (`export CLOUDSDK_CONFIG=<root>; cp ...`) is read as a root named and refused, which is the safe reading and a false positive the guard accepts. The transfer rule also reads the compose file. It recognises the call the way it recognises everything else -- another case, any run of whitespace, a run of flags with the value each takes in front of the subcommand (`docker --context <ctx> compose up`), `docker-compose` and the hyphenated sibling of each front-end as one word -- because `DOCKER COMPOSE`, `docker  compose` and `docker --context <ctx> compose` reach the same CLI and read the same file; and it resolves the file the way Compose does: the working directory first, then each directory the line `cd`s to -- each resolved against the directory the previous one reached, so `cd a && cd b` reads a/b rather than a target against the working directory -- then each parent of those until one holds a compose file. A `cd` target the shell builds is the one thing a text rule cannot read, so a compose call after `cd $VAR` is refused rather than passed, unless the file is named with `-f` and the directory never has to be found. A shell cannot be followed line by line by a text rule, so trying a directory Compose would not reach can only add a refusal, never a pass. Extend it with a case in `skill/test/gcloud-guard.test.mjs`; a residual that is deliberately left open must be a test named as a residual, never an expectation that reads like intended behaviour -- `skill/test/gcloud-guard.test.mjs` carries them as tests: a program that reads a file instead of copying it, a verb reached through a variable, a root the shell builds out of parts the text does not contain (a glob, a brace, a command substitution over a directory that is not itself a root), a copy tool that is not on the list, a compose file pulled in by `include:`, an ancestor of a root, a socket mount, and a root under a `DEVO_GCLOUD_PROFILES_DIR` other than the one this workstation keeps. A batch of rules is verified against the guard it replaces, not only against itself: the new test file is run from a `git archive` of the previous commit (which carries the previous guard), and every case whose verdict changes must be one of that batch's own cases -- a case that is green on both trees is a control or a residual, it measures nothing, and it has to read as one in the test file.
- The repository is the only source. `skill/install.sh` copies from `skill/` out to `~/.codex/tools/devo` (runtime), `~/.codex/skills/devo` (documents) and `~/.claude/hooks/` (the guard). Never edit an installed copy: the local change works immediately and the divergence is found much later, when it is no longer clear which copy is the truth. Edit under `skill/`, reinstall, then confirm with `cmp`. `skill/install.sh` also writes `~/.codex/tools/devo/INSTALLED.json`, one digest per copy -- every file of a copied tree at any depth, plus the two copies it writes rather than copies, the `~/.local/bin/devo` wrapper and the `~/.devo/config.example.json` example (the user's `config.json` is data, and is not recorded) -- and `devo doctor --provider install` compares every installed copy against it: a copy edited in place is a failure, while a repository copy newer than the install is only a warning, because that is the state between an edit and the reinstall that publishes it. Every destination the script writes into is made absolute first: the manifest records where a copy went, and a relative spelling would make the same install a failure from one working directory and a check that compared nothing from another. `CODEX_HOME`, `DEVO_BIN_DIR` and `DEVO_HOOK_DIR` accept an environment override, and the drift check reads the same three. The config directory does not: the example goes to `~/.devo` on every machine, and the check reads that fixed path, so the two agree by being fixed rather than by being overridden together. On the check's side, a recorded `installed` path that is not absolute is a failure rather than a path resolved against the doctor's own directory -- resolving it is how an edited copy reads as untouched from wherever the doctor happens to run -- a copy that is there and cannot be read is reported as unread rather than as changed, a manifest header field that is not a string is reported instead of being printed or thrown on, and a target named after an inherited property (`constructor`) is read as the name it carries rather than as whatever an object would answer with. Everything the manifest records is judged: an entry under a target the check does not know by name is reported under the name it carries rather than dropped, and a manifest that records no copies, or an entry that is not a record, is a failure -- a green header line above a manifest that says nothing would claim a verification that never compared a file. With no manifest at all, the check reads the install directories: copies on disk and nothing recording them is a failure with the remedy, because deleting that one file is the deletion that would otherwise turn the check green, while a machine with nothing installed is a skip -- a check that could not be made, which `allOk` keeps green without any file claiming to match. `skill/test/drift.test.mjs` covers each of those states.

## Implementation Notes

- Run `npm test` in `skill/` before pushing anything: it runs `node --test test/*.test.mjs` over the tenant doctor, the guard, the CLI refusals, the `exec` route, the drift check and the router's mutation guard, and no test touches the network. A case that goes through the router is written with a `gcloud` stub on PATH rather than the real program, so the suite can assert that a refusal happened *before* anything was started without reaching a cloud. `npm run check` syntax-checks every script and the hook.
- Every error the CLI raises deliberately is a refusal the caller can act on -- a missing flag, an unknown profile, a project outside the profile's scope. Print those as a message, never as a stack trace: a stack names internal paths and reads like a crash. `DEVO_DEBUG=1` restores the stack for genuinely unexpected errors.
- Keep the skill lightweight and deterministic. Add scripts only for repeated checks that are easy to verify.
- Do not add cloud SDK dependencies unless there is a clear reason; shelling out to installed `gcloud`, `aws`, and `doctl` keeps credentials in the user's existing local toolchain.
- Integration tests are required before adding backend or API services under a future `devo/agent/`.
