# Devo Agent Instructions

Devo is a DevOps specialist for cloud audits across GCP, AWS, and DigitalOcean.

## Operating Rules

- Default to read-only diagnostics. Do not create, update, delete, restart, resize, rotate, or deploy cloud resources unless the user explicitly asks for that action.
- Never print secrets, access tokens, private keys, full environment dumps, service account key contents, or unredacted credentials.
- Always state the cloud scope before running commands: provider, account/project, region, service, and time window.
- Treat tenants as isolated operational contexts. Do not mix findings, commands, costs, logs, or identifiers across tenants.
- Resolve tenant aliases through `devo.config.json` before running provider-specific checks when the user names a client/project alias.
- Prefer explicit command flags over global state changes. For GCP, use `--project` instead of `gcloud config set project` unless the user asks to change local defaults.
- For GCP, isolate human identities with separate `CLOUDSDK_CONFIG` roots on every CLI, proxy, and local ADC-consuming process. The local profiles are `master` (`sebastiano.cataudo@gmail.com`) and `nobrainer` (`seer@nobraineragency.com`); their credential files remain outside this repository under `/Users/zencrust/.config/gcloud-profiles/`.
- For AWS, verify `aws sts get-caller-identity` before querying resources and state the active profile/region when known.
- For DigitalOcean, require a tenant-scoped `doctlContext` and pass `--context` on every account or resource command. Never rely on the globally active context for tenant work.
- Cost checks should distinguish between estimated current-month spend, historical invoiced cost, and forecasted spend.
- Log comparisons should use a concrete time window and normalize timestamps, severity, service name, region, deployment version, trace ID, and request ID when available.

## Architecture

- Runtime CLI entrypoint: `skill/index.js`.
- Shared audit logic and tenant resolution: `skill/scripts/doctor.mjs`.
- Global tenant config path: `~/.devo/config.json`.
- Local development tenant config path: `./devo.config.json` in the repo root; this file is ignored by Git.
- Tenant config schema is documented in `devo.config.example.json` and `skill/references/tenants.md`.
- Installed command path: `~/.local/bin/devo`, generated by `skill/install.sh`.
- DigitalOcean tenant records use `provider: "digitalocean"` with a required `doctlContext`; optional fields are `teamName`, `defaultRegion`, `regions`, and `digitalOceanProjectId`. Credentials remain in the named `doctl` context and credential fields are rejected from Devo config.
- GCP identity-profile instructions live in `skill/references/gcp.md`. The repository stores profile metadata and paths only; never add gcloud `credentials.db`, ADC JSON, OAuth tokens, cookies, or exported credentials.
- `devo doctor --tenant <digitalocean-tenant>` verifies `doctl`, account identity, project visibility, and an optional configured project using the explicit tenant context. The command catalog covers identity, services, logs, costs, and IAM without changing the global `doctl` context.
- GCP identity runtime is split four ways: `skill/scripts/profiles.mjs` is the registry (name, account, root, health project, project patterns); `skill/scripts/gcloud.mjs` is the router, where `--profile` is mandatory and each call pins `CLOUDSDK_CONFIG`, the account and the project, refusing a project that belongs to another profile's scope and refusing a mutating `auth`/`config` subcommand unless `--allow-mutation` is passed; `skill/scripts/exec.mjs` is that same pin for a process that is not gcloud (`devo exec --profile <name> [--project <id>] -- <command...>`), which refuses any argument that names an identity root or a credential store so it can never hand one over, judging that argument by the path it denotes rather than by its text -- a root relocated through `DEVO_GCLOUD_PROFILES_DIR`, a symlink to one, a parent of one and the filesystem root itself are all refused, because each of them is a root or holds every root there is -- and applies the router's mutation guard to a `gcloud` command word reached through it (a `gcloud` call inside a shell wrapper is not inspected; `skill/test/exec.test.mjs` names that boundary as a residual); `skill/scripts/watch.mjs` is the hourly launchd watchdog (`com.zencrust.devo-auth-status`, installed by `devo auth watch --install`), which records one JSONL per profile under `~/.devo/auth-status/<profile>.jsonl`. The record path is derived from the profile for the same reason `CLOUDSDK_CONFIG` is: a single shared history was writable by two processes working on two identities, and it could not say which identity a count belonged to. Records written before the split are in `~/.devo/auth-status.jsonl` and are reported separately, never counted in with the rest.
- `skill/hooks/gcloud-guard.sh` is a Claude Code PreToolUse guard, deployed to `~/.claude/hooks/` by `skill/install.sh` and registered in `~/.claude/settings.json` under `hooks.PreToolUse` with `"matcher": "Bash"`. It denies an unprefixed `gcloud auth login` / `gcloud config configurations activate`, `--update-adc`, any read of a credential store, and any transfer of an identity root off the root it is protected in -- into a container or onto another host (`docker`/`podman`/`nerdctl run -v`, `--volume=`, `docker cp`, `ssh`, `scp`, `rsync`, `limactl`, `kubectl`), or into a copy or an archive on this disk (`cp`, `mv`, `tar`, `zip`). Both halves are one rule: a stray copy is the copy that gets committed. A verb is judged as the tool it names, not as the word it is written with: a directory in front of it (`/bin/cp`) and an escape (`\cp`) are read as the same tool, and both halves of the test are matched without regard to case, because on this filesystem another case is the same file. A root is also recognised by the variable that can name one (`CLOUDSDK_CONFIG`), because a relocated root carries none of the letters of the default path. `--update-adc` and the credential-store rule are judged before the trigger that looks for a `gcloud` spelling, since in a command like `devo auth repair master --update-adc` the flag is the only token naming identity material at all. A `CLOUDSDK_CONFIG=<root>` assignment that opens a shell segment is an environment pin for one local process, which is what the identity rules ask of every one of them, so the whole segment is dropped before that test; a root named as an argument is not dropped, so the mount, the copy and the build context stay denied. The exemption is that grammar, not the letters: a pin spelled as an argument to a builtin (`export CLOUDSDK_CONFIG=<root>; cp ...`) is read as a root named and refused, which is the safe reading and a false positive the guard accepts. The transfer rule also reads the compose file, which it resolves the way Compose does: the working directory first, then each parent until one holds a compose file. Extend it with a case in `skill/test/gcloud-guard.test.mjs`; a residual that is deliberately left open must be a test named as a residual, never an expectation that reads like intended behaviour -- `skill/test/gcloud-guard.test.mjs` carries them as tests: a program that reads a file instead of copying it, a verb reached through a variable, a copy tool that is not on the list, an ancestor of a root, and a socket mount.
- The repository is the only source. `skill/install.sh` copies from `skill/` out to `~/.codex/tools/devo` (runtime), `~/.codex/skills/devo` (documents) and `~/.claude/hooks/` (the guard). Never edit an installed copy: the local change works immediately and the divergence is found much later, when it is no longer clear which copy is the truth. Edit under `skill/`, reinstall, then confirm with `cmp`. `skill/install.sh` also writes `~/.codex/tools/devo/INSTALLED.json`, one digest per copy -- every file of a copied tree at any depth, plus the two copies it writes rather than copies, the `~/.local/bin/devo` wrapper and the `~/.devo/config.example.json` example (the user's `config.json` is data, and is not recorded) -- and `devo doctor --provider install` compares every installed copy against it: a copy edited in place is a failure, while a repository copy newer than the install is only a warning, because that is the state between an edit and the reinstall that publishes it. Everything the manifest records is judged: an entry under a target the check does not know by name is reported under the name it carries rather than dropped, and a manifest that records no copies, or an entry that is not a record, is a failure -- a green header line above a manifest that says nothing would claim a verification that never compared a file. With no manifest at all, the check reads the install directories: copies on disk and nothing recording them is a failure with the remedy, because deleting that one file is the deletion that would otherwise turn the check green, while a machine with nothing installed is a skip -- a check that could not be made, which `allOk` keeps green without any file claiming to match. `skill/test/drift.test.mjs` covers each of those states.

## Implementation Notes

- Run `npm test` in `skill/` before pushing anything: it runs `node --test test/*.test.mjs` over the tenant doctor, the guard and the CLI refusals, and no test touches the network. `npm run check` syntax-checks every script and the hook.
- Every error the CLI raises deliberately is a refusal the caller can act on -- a missing flag, an unknown profile, a project outside the profile's scope. Print those as a message, never as a stack trace: a stack names internal paths and reads like a crash. `DEVO_DEBUG=1` restores the stack for genuinely unexpected errors.
- Keep the skill lightweight and deterministic. Add scripts only for repeated checks that are easy to verify.
- Do not add cloud SDK dependencies unless there is a clear reason; shelling out to installed `gcloud`, `aws`, and `doctl` keeps credentials in the user's existing local toolchain.
- Integration tests are required before adding backend or API services under a future `devo/agent/`.
